# 判定机制详解

本文描述游戏（single-page three.js 应用）内部判定链的逆向结果。所有数值均来自页面 bundle 中的常量表。

## 0. 单位系统

| 概念 | 内部单位 | 显示 |
|---|---|---|
| 长度 | 1 | 5 cm |
| 冰淇淋直径 `creamDiameter` | 0.36 | 1.8 cm |
| 单层高度增量 `a` | 0.153 | 0.765 cm |
| band 高度 `bandHeight` | 0.72 | 3.6 cm |
| 底盘半径 `od` | 0.5 | 2.5 cm |

`a = creamDiameter / 2 × flattening = 0.18 × 0.85 = 0.153`

## 1. 高度

```
height = max(height, 落点y + a × radiusScale)
```

- **单调不减**，一旦达到就不会回落
- `radiusScale` 在正常堆叠中为 1，在收尾锥（`finish`）中从 1 降到 0.04
- 显示分数 = `floor(height × 5 × 10 + 0.5) / 10`

**推论**：单个落点最多把塔顶抬高 0.765cm。想更高，只能靠更多落点或更长存活时间。

## 2. 一个落点的三种命运

冰淇淋在指针位置挤出，延迟 `travelSeconds = 0.22` 秒后落地。落地位置为：

```
落点 = 0.6 × 挤出时的指针位置 + 0.4 × 当前指针位置
```

这构成一层天然低通滤波——指针的高频抖动会被削弱。

落地时按优先级走三个分支：

### 2.1 正常堆叠 `land`

| 步骤 | 规则 |
|---|---|
| 漂移修正 | 加上 `pileSlump`（静止时的缓慢漂移，`pileDrift = 0.08`） |
| 塔轴拉回 | `restPosition` 迭代 6 次，把落点朝塔的弯曲轴线拉（塔完全竖直时跳过） |
| 边缘钳制 | 若塔顶仍在底盘范围内，把落点钳到 `od + 0.18 × 0.95` 半径上 |
| **位移限速** | 落点从上一个点朝目标移动，**每帧最多 0.031 单位** |
| 高度求解 | `supportHeight`：遍历所有 `stroke` 差 ≥ 0.72 的旧点，取最高支撑 |
| 高度钳制 | 再限制在 `上一层y ± max(0.8 × 位移, 0.2 × 限速)` 内 |

**限速的来历**：`extrusionLengthPerSecond × fixedDt × 2.5 = 0.74 × 1/60 × 2.5 = 0.0308`

这是整局游戏的**根本速度上限**——任何策略都无法让落点单帧移动超过这个量。

### 2.2 挂载 `dropBelow`

**触发条件**（满足其一）：

1. `|目标点 − 上一点在塔轴上的投影| > creamDiameter/2 × missShift = 0.45`
2. 累计悬空 `overhanging > hangLength × creamDiameter = 0.36`

**行为**：

- 在目标周围 `0.36` 水平半径内寻找能接住的最高点
- 把新点挂到 `该点y + a × (1 + radiusScale) = 该点y + 0.306`
- 一次性把 `stroke` 推 `0.72`，并把 `overhang` 清零

第二条最为关键：**它绕过了「需要积累 0.72 的 stroke」这个隔离条件**，让每帧都能换层。

### 2.2.1 触发判据用的是「落点位移」

容易误读的一点：`dropBelow` 比较的不是落点离塔轴多远，而是**本帧落点与上一点塔轴投影之间的距离**：

```
|s − xd(o, bend)| > creamDiameter/2 × missShift = 0.45
  s = 0.6 × 挤出时的指针位置 + 0.4 × 当前指针位置
```

`s` 是 `landingPosition` 的输出（`travelSeconds = 0.22` 的混合缓冲），**不受落点限速影响**。所以真正的要求是**落点每帧位移 > 0.45**。

这一条同时解释了两件事：

- 慢速轨迹（哪怕离轴很远）永远不会触发——每帧位移可能只有 0.03
- 高频切顶点也有临界——三角形 `R = 0.51` 时混合位移只有 0.467，仅比阈值高 4%

`dropBelow` 内部在目标周围 `creamDiameter = 0.36` 水平半径内寻找可接住的最高点，权重随距离衰减：

```
√(1 − (d / u)²)      u = 0.36
```

`d` 超过 0.36 时这个点完全不可用。**这解释了多边形轨迹的停滞现象**：三个方位固定不动时，塔柱会长在同样的三个方位上；一旦目标点与柱子的水平距离超过 0.36，就再也挂不上去，页面高度冻结，而模型仍然在涨。

给多边形加缓慢自转（`spin`）可以让柱子方位持续漂移，绕开这个死锁。

**这个 `d` 同时决定增益大小，是整局最深的一处矛盾：**

- 触发捷径要求落点距塔轴 > 0.45
- 但每次挂载的高度增益是 `0.153 × √(1 − (d/0.36)²)`，`d → 0` 时最大（0.153 单位 = 0.77cm），`d → 0.36` 时归零

同一个 `d` 两头拉：落点离轴越远越容易触发，挂上去的层却越矮。实测的 30cm/s 就是这样被锁住的——不是「触发率不够」，而是触发了也涨不满。这也是为什么单靠调参数突破不了 250：任何提高触发率的改动都在同时压低单次增益。

**塔必须弯曲才能持续被挂上。** 落点固定在半径 0.66 处，而可挂载的点必须距落点 < 0.36，所以塔顶得先偏移到离轴 0.30 以上。塔的 `bend` 由累积倾角提供——这正是 `spin` 的作用：让落点方位跟着弯曲方向走，而不是撞死在固定方位。

### 2.2.2 为什么离散跳点更快

圆周轨迹的落点是连续变化的。指针追上目标之后，两者的水平距离会缩回 0.45 以下，`dropBelow` 的触发条件断开，落点被迫回到普通的 `land` 分支（每层只加 0.153）。

多边形则是**离散跳变**：正 N 边形顶点距轴 `R` 时，相邻顶点间距为 `2R·sin(π/N)`。取 `R = 0.51`：

| N | 顶点间距 | 是否越过 0.45 触发线 |
|---|---|---|
| 3 | 0.883 | ✓ |
| 4 | 0.721 | ✓ |
| 6 | 0.510 | ✓ |
| 8 | 0.390 | ✗ |

每次换顶点都是一次远超阈值的瞬移，于是捷径被高频触发。但**边长越大越好**，因为混合位移只有边长的 0.529 倍：

| R（三角形） | 混合位移 | 实测触发率 |
|---|---|---|
| 0.51 | 0.467 | 74% |
| 0.58 | 0.542 | 92% |
| 0.66 | 0.615 | 94% |

`R` 也有上限：`rimPosition` 会把半径超过 `od + creamDiameter/2 × 0.95 = 0.671` 的落点钳回去，`R = 0.70` 因此会触发 `spill`。

边数同样不是越多越好。实测只有 N=3 有效——N=5 只有 139cm，N=6 只有 27.8cm。

**边数也不能再往下减到 2。** 混合缓冲窗口是 13 帧（`0.22 × 60 = 13.2`），13 是奇数，两点交替时相邻两帧的落点必然分别取自两端，即 `0.6B + 0.4A` 与 `0.6A + 0.4B`，位移等于 `0.2 × |A−B|`——两项反向，抵消掉大半。两点最大距离是对径 `2R = 1.32`（受 `rimPosition` 的 0.671 钳制），位移上限 0.264，只有阈值的 59%。实测 76.4 / 42.4 / 26.1 cm。

三角形不抵消，是因为 `13 mod 3 = 1`，相邻两条边向量夹角 120°，余弦为负反而成了加项。

| N | 边长 | 位移系数 | 混合位移（R=0.66） | 页面实测 |
|---|---|---|---|---|
| 2 | 2R = 1.32 | 0.200 | 0.264 ✗ | 76.4 |
| 3 | 1.732R | 0.529 | 0.615 ✓ | 217 ~ 248 |
| 4 | 1.414R | 0.721 | 0.673 ✓ | **0.0** |
| 6 | R | 0.872 | 0.575 ✓ | 27.8 |

N=4 的混合位移全场最高，页面却一个点都堆不起来。**位移过阈值只是必要条件**，方位分布还得能持续找到挂载点（见 2.2.1 末尾的 0.36 半径衰减）。

**半径也有下界。** `p ≈ 0.03` 时落点每帧位移约等于 `R`，要越过 0.45 就得 `R ≳ 0.45`。实测 R=0.35 只有 1.4cm（平台期），R=0.45 是 137cm，分界就落在这条线上。

小半径还有第二个效应：`stroke` 的增速是 `+= hypot(位移)`，而位移被限速在 `0.0308/帧`，所以**每层所需时间正比于 `1/R`**。R=0.15 时约 0.67 秒一层，比运行器的 0.6 秒 stall 窗口还长——正常堆叠会被误判成停滞并提前松手，表现成 `0.0cm`（影子模型 `generated` 只有 0.045，即 36 个物理步）。放宽窗口到 3 秒后同参数能到 23cm 才倒。

**理论上唯一的例外，实测更差。** 让 13 帧缓冲完全对齐（`13ω ≡ 0 (mod 2π)`）能把缓冲因子从约 1 抬到 1.985，理论上 `R = 0.227` 就够。但此时落点塌缩成指针本身、沿圆周连续漂移，一个点都堆不起来（实测 0.0 / 0.0 / 1.4）。

所以半径被夹在 `[0.45, 0.671]` 之间：下限是触发线，上限是 `rimPosition` 的钳制。

### 2.3 洒了 `spill`

```
canCatch(x, z) = hypot(x, z) < od + creamDiameter/2 + rimGrip = 0.73
```

若直接判断失败，会用 `restPosition` 把落点拉回塔轴后再判一次。两次都失败则 `fail('spill')`，**游戏立即结束**。

## 3. `supportHeight` 与 `stroke` 隔离

```
supportHeight(x, z, 基础高度, 过滤条件) =
    遍历所有 points（从最旧开始）：
        若 stroke_current − stroke_point < 0.72  →  break
        若水平距离 < 该点半径        →  s = max(s, 该点y + 支撑高度)
```

`points` 按时间顺序存储，`stroke` 单调递增，所以：

- **只有「够旧」的点参与支撑**
- 紧邻的 0.72 stroke 窗口内的点，全部被忽略

这就是「每层 0.38 秒」的来源：`0.72 / 0.0308 ≈ 23 帧 ≈ 0.38 秒`。

**高速大圈**之所以有效，就是因为快速旋转让 `stroke` 以接近上限的速度累积，于是支撑集迅速退化成「几乎只有上一个独立层」，每层能涨满。

## 4. 失稳判定 `balance`

塔按 band 建模（每 `bandHeight = 0.72` 一个 band），每个 band 有质量、质心、倾角 `(ax, az)`。

每层的驱动力矩：

```
力矩 = 质量 × gravity × max(0, 质心偏离下层支撑轮廓的距离)
抗倾覆 = adhesion × 宽度³ / 半径
刚度   = stiffness × 宽度^stiffnessExponent × 细塔惩罚 / 半径
```

其中宽度受 `widthLimit = 1.1` 硬性截断，细塔惩罚为 `min(1, 宽度/0.7)^9`。

**失败条件**（满足其一）：

| 类型 | 判据 | 物理含义 |
|---|---|---|
| 单层 | `|ax,az| / breakAngle(0.5) ≥ 1` | 单层歪超过 28.6° |
| 整塔 | `hypot(Σax, Σaz) / toppleLean(1.2) ≥ 1` | 各层倾角叠加超过 68.8° |

**为什么越高越难**：上层质量压在下层上的力臂随高度线性增长，同样的质心偏移会产生更大的倾角。宽度被 `widthLimit` 卡死后，无法通过「堆得更粗」来抵消。

## 5. 结算判定 `settling`

松手（`pointerup`）后进入结算等待：

```
settling = !pouring && (还在空中的冰淇淋数量 > 0 || (未失败 && 塔未静止))
```

两个条件都要清空：

1. **空中冰淇淋落完**——`pending` 队列，最多再等 0.22 秒
2. **塔完全静止**——`resting = 最大角速度 < restSpeed(0.03)`

随后：

- `failureReason === null` → **完成！计入记录**
- `failureReason !== null` → **失去平衡了，不计入记录**

### 松手后的额外收益

松手瞬间若空中仍有冰淇淋、且能接住，会进入 `finish` 分支：

```
高度 = 上一落点y + creamDiameter/2 × 1.25 × smoothstep(t)
半径缩放 = max(0.04, (1 − t)^0.65)
```

这一步会把剩余体积一次堆成收尾锥，**最多再加约 1.1cm**——实测最终成绩通常比停手时显示的高 1.5~2cm。

## 6. 帧率与物理步

物理以 `fixedDt = 1/60` 累积推进。渲染帧率**低于** 60fps 时，累加器来不及补齐，物理步会被丢弃——页面高度按物理步数增长，于是成绩随帧率塌陷：

| 帧间隔 | 成绩（同参数） |
|---|---|
| 6.3ms（158fps） | 214.8 |
| 17~21ms（48~58fps） | 35 ~ 102 |

反过来，帧率**高于** 60fps 没有额外收益：解锁 vsync 跑到 3400fps 与 158fps 成绩一致。所以只需保证不掉帧，用 `--disable-gpu-vsync --disable-frame-rate-limit` 启动可消除外部负载导致的抖动。

## 7. 收手时机

运行器把物理类的一份副本并排跑在页面里，作为状态传感器。它与页面吃到相同的输入，但状态独立演化，因此会**先一步**判定倒塌（提前 0~1.5 秒）。

但收手判据不止一种，实测完成率差别很大：

| 信号 | 触发时机 | 完成率 |
|---|---|---|
| `modelfail` | 影子模型自己判倒 | 约 2/3 |
| `stall` | 页面高度 0.6 秒没涨 | 约 1/6 |
| `stopCm` | 高度到达设定值 | 约 1/6 |

`stall` 意味着页面已经**真的**饱和——支撑点再也找不到更高的位置，此时塔的结构已经到极限，松手后几乎必倒。

**但完成率高不等于成绩高。** `modelfail` 出现时高度已经被钉死了（塔已到临界）。改成到固定高度（`stopCm`）立刻松手，塔还有余量，能在 1.5~3.5 秒内晃稳，最终成绩反而更高。成功带在 244~246cm，最终记录 248.7cm 就是这么拿到的（`spin` 取 0.20）。

**离线模型不能预测成绩。** 用同一份物理类离线跑，结算阶段每次都成功（圆周 `p=0.03` 停 9.5 秒能到 280cm 完成），但页面同配置从未超过 214cm。帧时刻抖动会放大混沌，离线只适合筛选候选轨迹。
